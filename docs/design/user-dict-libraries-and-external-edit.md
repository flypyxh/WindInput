# 用户分库与外部编辑

状态：已实现，随 v0.127.0-beta.1 发出（定稿时维护者审阅后改：分库放独立目录、开关放上层配置文件、词库窗三栏、数据文件头加一行说明）。

## 1 目标

- **用户分库**：用户把自己的词表分成多个文件，各自开关。新造的词仍进主用户词库（维护者定：只读分库，不做多个可写库）。
- **外部编辑**：设置里可以直接打开数据目录或某个数据文件，用编辑器批量改，改完程序接着用，不再靠「导出 → 改 → 导入」。
- **数据文件自述**：`data/` 下目录和文件多，每个文件第一行写明它是什么、能不能手改（§5）。
- 导入导出格式的统一另起一份设计，本文只在 §6 记它与本文的接口。

## 2 实施前现状

- 用户词只认 `data/<数据方案>/user.dict.yaml` 一个文件：路径、`dict.reload` 白名单、引擎的 (target, schema) 绑定、日志记录都只有这一维（`wind-store/src/store.rs:431`、`user_words.rs:603`、`wind-userdata/src/record.rs:12`）。
- 扩展词库已经是「用户自放、可开关」的词库：`[[dictionary_dirs]]` 或默认 `<主词库目录>/ext` 下的 `*.dict.yaml` 在读方案时自动登记（`wind-engine` 的 `inject_dir_dicts`），id 为 `dir:<相对路径>`，出厂关，开关按方案存在 `schema_overrides/<方案>.toml`（`schema.setDictEnabled`）。它是系统层：码表按 `base_order` 排在主库后，拼音并进系统词库的分层缓存按权重比。
- 扩展词库在设置里只出现在「方案管理 → 扩展词库」，只能开关；新增要点「打开目录」放文件、重开窗口；改文件内容后 `dict.reload` 不管，要等方案重建。
- 外部改 `user.dict.yaml` 已有基础：启动 / 切方案 / 配置重载时按内容指纹同步，`dict.reload` 可手动触发；写回前复核指纹，不一致就放弃本轮、退避重试。剩余风险是**编辑器开着旧内容时程序写回、用户随后保存**，程序写进去的行被盖掉，之后以文件为准，这些词就丢了。
- 设置端已有 `open_with_default_app`（`wind-setting/src/open_external.rs`）。

## 3 用户分库

### 3.1 定义

```
data/<数据方案>/
  user.dict.yaml        主用户词库（新词写这里）
  dicts.toml            分库开关
  dicts/
    成语.dict.yaml       用户分库，一个文件一个
    行业词.dict.yaml
```

`data/<数据方案>/dicts/` 下每个 `*.dict.yaml` 是一个用户分库，不递归子目录。格式与 `user.dict.yaml` 相同（Rime 词库，列 `text, code, weight`，可省权重）。分库名取文件主名；显示名优先取词库头的 `name:`。

开关放在上一层的 `dicts.toml`，按方案记**关掉的**分库（出厂全开，新放进来的分库自动开）：

```toml
# 清风输入法 · 用户分库的开关（按方案）。可在设置里切换，也可手动修改。
[schemas.pinyin]
off = ["行业词"]

[schemas.shuangpin_xiaohe]
off = []
```

- 键是方案 id（不是数据方案）：全拼与双拼共用 `data/pinyin/dicts/` 的文件，开关各自独立，与扩展词库的现行语义一致。
- 文件里记了但已不存在的分库名忽略；分库改名时由 core 的 `userDicts.rename` 一并改这里。
- 读不了（格式坏）时按全开处理，并在 `storageStatus.issues` 报出；设置里切换开关时整文件改写前先把坏文件按 §2.5 改名留存。

### 3.2 复用扩展词库机制，不另建一套

P2c 曾裁定「用户分库并入扩展词库目录，不另建机制」，理由是两处入口、两处配置。本设计保留「不另建机制」，只是给扩展词库**多一个来源目录**：

| | 扩展词库（现有） | 用户分库（新增） |
|---|---|---|
| 位置 | `schemas/<主词库目录>/ext` 等 | `data/<数据方案>/dicts/` |
| 面向 | 方案作者、随包细胞词库 | 用户自己的词表 |
| id | `dir:<相对路径>` | `user:<文件主名>` |
| 档位 | 系统层，排在主库后 | 排在系统库之前，与用户词同档 |
| 出厂 | 关 | 开（用户自己放进来的，默认就要用） |
| 备份 / 外部编辑 | 随 `schemas/` 整树 | 随 `data/`，与用户词一起 |

发现、编译缓存（按内容指纹，没变不重编）、启停生效路径沿用；开关存储不同：`schema.setDictEnabled` 对 `user:` 前缀的 id 写 `dicts.toml`，登记时从它取 `enabled`。与 P2c 的差别只在「用户的东西放在用户数据目录里」：备份、外部编辑、文档里讲「你的数据都在 `data/`」都更顺。

- **档位**：码表用 `base_order = -3`（与用户层 `LayerType::User` 相同）。拼音的扩展库并进系统词库分层缓存、按权重比，分库同样处理；无权重的分库行取方案的 `default_weight`。
- **开关按方案**：全拼与双拼共用 `data/pinyin/` 的文件，开关各自独立，与扩展词库的现行语义一致。
- **删词**：界面里删分库的一条 = 改该文件（按行补丁 + 指纹复核 + 原子替换），随后失效相关方案；不走 Shadow。Shadow 仍可对任何词置顶 / 删除。
- **改了文件怎样生效**：`dict.reload` 认 `data/<数据方案>/dicts/*.dict.yaml` 与 `dicts.toml`，做「失效用到该数据方案的方案」。指纹没变就不重编，代价是一次方案重建。

### 3.3 设置端

词库窗是三栏：数据域 | 类别 | 内容（2026-10-16 维护者验证后改，原先的分库切换器与「管理…」对话框不再保留）。

- **中栏**列出当前数据域的类别；方案域的「用户词库」下再列「主词库」和各分库。分库前有勾选框直接开关，后面是条目数；停用只靠勾选框表达，文字不变灰，仍可点开查看。外部编辑期间弹模态对话框（§4.2）。
- 栏顶是数据域名，有分库的方案多一个「+」：新建分库、从文件导入为分库（第三方格式先转成 Rime 格式再落盘）、打开分库目录。
- 每个节点右键给它能做的事（右键先选中该节点）：
  - 用户词库：同「+」。
  - 分库：启用 / 停用、编辑文件、重命名、打开分库目录、删除（二次确认）。
  - 其余类别与主词库：编辑文件、导入、导出（按这一类的能力），以及打开数据目录。
- **右栏**顶部是标题（「用户词库 · 成语」）与这一类的文件操作；选中分库时表格可增、改、删、清空，可多选，「移动到…」把条目移到主词库或别的分库；没有导入导出——导出就是分库文件本身。
- **左栏**条目右键「打开数据目录」；底部「刷新」= 让 core 重读数据文件（文件没变只比指纹）再刷新列表，有变化才提示。
- 扩展词库仍在「方案管理」里，不搬。

### 3.4 不做

- 多个可写分库、新词写入指定分库。

条目移动已实现：主词库与分库之间、分库之间都可「移动到…」（§3.3）。

## 4 外部编辑

### 4.1 可编辑的文件

`data/<数据方案>/user.dict.yaml`、`shadow.dict.yaml`、`temp.dict.yaml`、`freq.table.yaml`、`dicts.toml`、用户分库，`data/phrases.dict.yaml`、`quick_format.toml`、`common_chars.yaml`、`charsets/*.yaml`。

`data.beginEdit` / `data.endEdit` 的目标：`{path}`，或按类别 `{kind: words|shadow|temp|freq|user_dicts, schemaId}`、`{kind: user_dict, schemaId, name}`、`{kind: phrases|quick_format|common_chars}`、`{kind: charsets, key}`（方案按数据方案换算，拼音族折叠到 `pinyin`）。

- **临时词 / 词频**（`temp`、`freq`）：与用户词同一套——开始时先折回、没有文件按空表新建、暂停写回；编辑期间照常学习（进日志与 delta），结束时同步、新学到的按键合并进用户改过的文件，删掉的行不复活。编辑期间界面的删除 / 清空 / 转正 / 导入拒绝；引擎层对暂停中的目标拒绝整体替换与带策略的整写。
- **字符分类**（`charsets`）：按 key 开始；出厂与用户层都没有的 key 拒绝；用户层还没有这个类的文件就先写一份只带 key 的（说明行 + 头部）。结束时随字符分类重建按出厂校验：解析不了或 key 与文件名不一致 ⇒ 整份不生效；出厂类改 `ranges`、写 `replace: true` ⇒ 去掉这两项、其余照用。两种都登记为 `{kind: "invalid", file, message}`，`data.endEdit` 在重建之后取问题带回，修好后消失。

不开放：`draft` / `assoc` / 补全 / 统计。这些由程序高频写入，人工编辑价值低、冲突风险高，入口上不提供（文件本身不加锁，用户硬改照现有同步规则处理）。

### 4.2 编辑会话

```
设置端「编辑文件」 → data.beginEdit {file}
   core：该文件对应的目标先折回一次（文件里有全部数据），然后暂停它的写回
   返回绝对路径 → open_with_default_app
设置端弹模态对话框「正在编辑 xxx  [打开所在文件夹] [再次打开文件] [完成并加载]」（ESC / 关窗 = 完成并加载）
用户在编辑器里改、保存
「完成并加载」 → data.endEdit {file}
   core：按文件同步（与 dict.reload 同一路径）→ 恢复写回 → 返回解析问题（坏行号与原因）
```

- 编辑期间照常打字、造词：新写入留在日志和 delta 里，查询不受影响；恢复写回后按行补丁落到用户改过的文件上，不会丢。这是会话相对「直接打开文件」的全部价值。
- 小表（短语、Shadow、快捷格式、常用字、字符类）编辑期间，界面里对同一张表的修改先挡住，提示「正在外部编辑」。
- **租约**：会话记在 core 内存里；关词库窗时由设置端结束会话，设置进程崩溃则靠租约——2 小时内既没有再次打开也没有保存文件，自动结束（按「完成并加载」处理；同步失败也照样结束会话、恢复写回，文件之后走隔离 / 退避）；core 重启后不存在会话，所以不会卡死写回。
- 解析问题：坏行跳过并计数、整份坏则隔离不折回，沿用 §2.5 的统一策略；`endEdit` 把问题列表带回，对话框直接展示，可「再次打开文件」修改。

### 4.3 不走会话的直接编辑

用户用资源管理器自己打开文件改也行，沿用现有规则：写回前复核指纹，启动 / 切方案 / 配置重载时同步。词库窗左栏的「刷新」会先调 `dict.reload`；「打开数据目录」在左栏和中栏的右键里。文档里写明：编辑器开着文件时，别让程序写回之后再保存旧内容——推荐用「编辑文件」入口。

## 5 数据文件的一行说明

`data/` 下程序写出的每个文本文件，第一行是一行注释，说明用途和能不能手改：

```
# 清风输入法 · 拼音的用户词库（造的词、加的词都在这里）。可手动编辑词条；文件头（--- 到 ...）请勿修改。
---
columns: [text, code, weight]
...
```

| 文件 | 说明行要点 |
|---|---|
| `<数据方案>/user.dict.yaml` | 用户词库；可编辑词条 |
| `<数据方案>/dicts/*.dict.yaml` | 用户分库；可编辑词条（只在程序新建或导入时写说明行，用户自己放进来的文件不动） |
| `<数据方案>/dicts.toml` | 分库开关；可编辑 |
| `<数据方案>/shadow.dict.yaml` | 候选调整（置顶 / 删除）；可编辑 |
| `<数据方案>/temp.dict.yaml`、`freq.table.yaml` | 程序自动学习的数据；可经「编辑文件」修改，编辑期间学到的完成后合并 |
| `<数据方案>/draft.dict.yaml`、`assoc.table.yaml` | 程序自动学习的数据；请勿手改 |
| `phrases.dict.yaml` | 用户短语与对系统短语的修改；可编辑 |
| `quick_format.toml`、`common_chars.yaml`、`charsets/*.yaml` | 快捷输入 / 常用字 / 字符类的个人调整；可编辑 |
| `completion.table.yaml`、`stats/*.toml` | 程序维护的补全历史 / 统计；请勿手改 |
| `<用户目录>/meta.toml` | 数据格式版本；请勿手改 |

- 说明行由程序生成，**不参与解析**；整文件重写时按当前文案重新生成；按行补丁时，文件直接以 `---` 开头（无 BOM）就在最前面补上说明行（行尾随文件），第一行是注释（含用户自己写的）或带 BOM 则原样保留。用户删掉它不算格式错误，下次整文件重写时补回。
- 文案集中在一张表里（`wind-userdata/src/text/banner.rs`），各写出路径从表里取，不各写各的。字符分类那行由 wind-config 渲染，表里另存一份，有测试锁两份一致。
- 「可编辑」的统一后缀：「可手动编辑；文件头（--- 到 ...）请勿修改」（TOML 文件写「可手动编辑」）。「请勿手改」的统一写「由程序自动维护，请勿手动修改」。临时词 / 词频写「可在设置里用「编辑文件」修改，编辑期间新学到的内容会在完成后合并；文件头（--- 到 ...）请勿修改」。
- **启动补写**：打开用户数据时、绑定任何数据之前扫一遍 `data/`（不进 `.backup/` 与 `dicts/`）：程序写的文件第一行不是说明行就补上，第一行是旧文案的说明行就换成当前的，走原子写。之后各处按新内容取指纹，引擎文本目标按「文件变了」由文本重建、未折回的操作留在 delta 照常叠加，不丢。不动：用户自放的分库、带 BOM 的、词库 / 表格文本第一行是别的注释的（用户自己写的；小表旧文件第一行的格式说明照补）、解析不了的。补过的文件下次只读第一行。

## 5.1 备份与坏文件留存

- 整文件提交前的上一版放 `data/.backup/<相对路径>`（同名），数据文件旁边不再有 `.bak`。数据目录在 store 打开时登记（按路径前缀认领，进程内可登记多个，测试各用各的临时目录）；不在登记目录下的文件仍用旁边的 `.bak`。
- 解析不了而留存的坏文件放 `data/.backup/<相对目录>/<文件名>.corrupt-<UTC 时间>[-N]`，每个原文件只留最新 5 份；问题里的 `kept_as` 是相对数据目录的路径。
- 机写文件（补全、统计）自愈先读 `.backup/` 里的上一版，没有再读旧版旁边的 `.bak`。
- 首次启动时把旧版留在旁边的 `*.bak` 与 `*.corrupt-<时间>` 挪进 `.backup/`（相对路径不变），只跑一次（跑完在 `.backup/.migrated` 留标记），之后用户自己放的 `.bak` 不动。只认程序数据文件的：`.bak` 还要原文件在；坏文件留存按名字形状认。不删任何文件：`.bak` 在新位置已有一版就按修改时间留新的，新位置那份更旧就另存为 `<名>.older`，旁边那份更旧就留在原处。迁移时不按 5 份裁剪；重名的坏文件留存续 `-N`，仍是留存名。
- 分库改名带走它的上一版，删除一并删掉；小表删文件同样删它的上一版。
- 扫描数据目录的地方都跳过 `.backup/`（方案目录列举、整机备份）；整机备份不打包它。

## 5.2 用户分库的界面增删与按方案删数据

- `userDicts.addEntry {schemaId, name, text, code, weight?}` → `{ok}`：按 (词, 码) 去重，已有的改成给的权重（可调低），没给权重就不动；新词没给权重时权重列留空（按方案默认）；权重不是整数、或分库没有权重列却给了权重 ⇒ 报错。`userDicts.clear {schemaId, name}` → `{ok, removed}`：保留文件头与说明行，以及仍在注释区的注释行（`# no comment` 之后 `#` 开头的是词条，一并删）。都走按行补丁 + 指纹复核，外部编辑中拒绝，改了失效用到该数据方案的方案。码 / 词不能为空、不能含 tab 或换行。
- `userdata.purgeSchema {schemaId}` → `{ok, removed}`：删数据方案目录、`.backup/` 里它的那份与 `schema_overrides/<id>.toml`；先清各目标让待写回的操作摘掉，再删目录、失效引擎。与别的已装方案共用数据 ⇒ 拒绝「与「<名>」共用数据，不能单独删除」——「共用」按各方案实际写入的数据方案算：拼音族都写 `pinyin`，混输的码表一侧写主方案的数据方案、有拼音子方案时拼音一侧写 `pinyin`。混输方案自身 ⇒ 拒绝「混输方案的数据在「<主方案名>」和拼音里，请在那里删除」。未安装的方案、`stats` / `charsets`（不分大小写）这类保留目录 ⇒ 拒绝。有文件正在外部编辑 ⇒ 拒绝。统计不动。
- `data.locate` 的返回多一个 `exists`（目标此刻在不在）；带 `schemaId` 时再多 `purgeable`，为 false 时带 `reason`（与 purgeSchema 拒绝时同一句，同一个判据）。设置端只在 `exists && purgeable` 时给删除入口。

## 6 与格式统一的接口

格式统一另立设计，本文只定一个方向：**自有交换格式就是 `data/` 下的真源文件**。用户分库是落地的第一步——「导入为分库」的结果就是一个真源格式文件，导出一个分库就是拷贝它。备份包现在逐表重新序列化（wdict / jsonl），用户分库在本设计里先按文件原样进包（`data/<数据方案>/<名>.dict.yaml`，type `user_dict_file`），整个备份改成「打包 `data/`」放到格式统一那一份里做。
