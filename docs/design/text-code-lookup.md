# 按词查编码：系统词库与用户词库作为整体

状态：第一期已实施（分支 feat/aux-code-source，见 §6 分期表提交号）。
起因：辅助码要支持「引用一个方案」（`docs/design/aux-code-schema-source.md`），讨论中确认
「用户词库应与系统词库作为一个整体」不是辅助码独有的需求，而是所有「按词查编码」使用方的共同缺口。

## 1. 现状

「编码 → 词」是输入主路，系统词库与用户词库早就一起查。反方向「词 → 编码」则各查各的：

| 使用方 | 入口 | 查什么 | 用户可见的后果 |
|---|---|---|---|
| 候选注释 `${code}`、悬停 [编码] 段 | `comment.rs` → `word_codes_in` / `codetable_reverse_hint` | 仅系统反查索引 | 自己造的词、自己加的字不显示编码 |
| 拼音方案下显示主码表编码 | `codetable_reverse_hint` | 仅系统 | 同上 |
| 码表造词取单字全码 | `single_char_codes`（`encode_word` 的数据源） | 仅系统 | 用户给某字加的编码，造词公式用不上 → 含该字的词造不出来 |
| 词语联想 | `assoc_prefix_words` | 系统反查索引 + **自带的**用户词文本索引（`user_assoc.rs`） | 能用，但那份用户层只收两字以上、只一个槽 |
| 加词去重 | `handle_addword::encode_and_dedup` | 系统（反查索引）与用户（`get_user_words` 按码查）**分两道** | 无——分层查是有意的，见 §5 |
| 辅助码（新） | — | 需要系统 + 用户 | — |

用户词在 store 里按 `schema\0code\0text` 排序，按词查只能扫全表（用户词库实测可达十九万条），
所以没有一个使用方能在按键线程上直接查。词语联想的解法——内存里按文本排一份、写代次过期、
后台单飞重建——是目前唯一跑通的形态。

## 2. 目标

在 `EngineManager` 上提供**一个**「词 → 编码」入口，按层给出结果：

- 系统层：该方案启用的系统词库；
- 用户层：该方案的用户词；
- 临时层：该方案的临时词（自动造词、未确认）。

各使用方**自己选层**，不把所有层硬合成一个答案——几个使用方的口径本来就不同（§5）。

非目标：用户隐藏（shadow）的系统词不在本入口扣除（首版口径，辅助码设计里已确认）；
按词前缀查（词语联想用）作为同一入口的第二个查询方法提供，但联想的迁移不在第一期。

## 3. 结构

```
EngineManager::text_codes(schema_id) -> TextCodeView      // 不阻塞，可能缺层
TextCodeView {
    system: Option<Arc<ReverseIndex>>,     // None = 尚未就绪
    user:   Option<Arc<UserTextIndex>>,    // None = 尚未就绪 / 无 store
}
impl TextCodeView {
    fn codes_of(&self, text: &str, layers: Layers) -> Codes;       // 各层按序拼接、去重
    fn with_prefix(&self, prefix: &str, layers: Layers, limit) -> …; // 第二期，供联想
}
Layers = SYSTEM | USER | TEMP 的位组合
```

### 3.1 系统层：沿用反查索引，不新建数据结构

`ReverseIndex` 已按「词 → 全部编码，码长升序」建好，有落盘缓存与单飞构建。本入口直接用它。

要改的一处：**保留策略**。`reverse_index_for` 现在建完就 `retain(k == 本次 || k == 主码表)`，
全进程至多两份。加入辅助码后，同时在用的方案可能有三个（主码表、联想方案、辅助码引用的方案），
两份的上限会让它们互相顶掉、反复秒级重建。改为保留**当前在用集合**：

```
在用集合 = { code_source_schema, assoc_word_schema, 活跃方案折叠后的辅助码引用方案… }
```

在用集合在切方案 / 配置重载时重算，不在集合里的索引释放。内存上限的顾虑仍在（大方案一份上百 MB，
但大头是 mmap，不计 Private，见记忆 windows-private-vs-workingset），在设计里记下，实测后再定是否设上限。

### 3.2 用户层：推广词语联想的用户词文本索引

`user_assoc.rs` 的 `UserAssocIndex` 已经是「按文本排序的紧凑表 + 写代次 + 后台单飞重建」。
推广为 `UserTextIndex`（挪到独立模块，联想改为它的使用方之一），三处改动：

1. **收全部长度**：今天只收两字以上（联想用不到单字）。按词查编码要单字。
2. **收全部编码**：今天同一文本只留排序键最大的那条码。按词查编码要该词的全部编码。
   表项改为「文本 → 码列表」，联想取首码即可，行为不变。
3. **按方案分槽**：今天只有一个槽，放当前联想方案。辅助码引用的方案（如五笔）与联想方案
   （拼音）同时在用，共用一个槽会互相顶掉。改为按 `data_schema_id` 分槽，淘汰规则与 §3.1
   的在用集合一致。

**写代次按方案计**：`Store::words_generation` 是全局的——在拼音里打字自动造词，会让五笔的用户层
也判过期、后台重扫。给 store 加 `words_generation_of(schema)`：`bump_words_gen` 的调用点
（`user_words.rs` / `temp_words.rs` / `draft_words.rs` 共十余处）绝大多数写的是单一方案，
改为同时推进全局与该方案的计数；`Store::resume`（整库恢复）这类不分方案的写入推进一个
「全体纪元」，`words_generation_of` 返回「全体纪元 + 该方案计数」的组合，任一变化即过期。
全局计数保留（现有使用方不动）。

**只在用到时检查**：查询时发现过期，本次照用旧的，起后台重建。不监听写入——没人查的方案一次都不扫。
刚写入的词晚一次查询生效。

临时词：`UserTextIndex` 内分用户、临时两张表（今天就是这样），由 `Layers` 决定取哪张。

### 3.3 就绪语义

沿用 `word_codes_in` 的三态约定，但按层表达：`TextCodeView` 里某层为 `None` 就是「这一层还没就绪」，
不是「查不到」。展示类使用方把缺层当作空；需要确定答案的使用方（加词去重）另有阻塞入口，
行为不变。

## 4. 第一期接入的使用方

| 使用方 | 取层 | 变化 |
|---|---|---|
| 辅助码（新） | SYSTEM + USER | 字 → 编码，见辅助码来源设计 §4 |
| 候选注释 `${code}` / 悬停 [编码] / `codetable_reverse_hint` | SYSTEM + USER | 自己造的词、加的字开始显示编码 |

`codetable_reverse_hint` 取「最长码」的口径不变：按层拼接后仍取全部码里最长的那个。

## 5. 以后再迁的使用方（逐个核实口径）

- **码表造词取单字全码**（`single_char_codes`）：用户加的单字编码进入造词公式是明确的收益，
  但全码判据（码长上限闸、最长码、权重、字典序）要对用户层重新论证——用户词没有「简码 / 全码」
  之分的保证，拿一个用户随手加的短码当全码会造出错码。单独立项。
- **词语联想**：已经是系统 + 用户 + 临时，迁到本入口只是去掉它自带的那套，行为应不变；
  放在第二期，用 A/B 对拍验证。
- **加词去重**：**不迁**。它分两道查是有意的——系统层用反查索引，用户层用 `get_user_words`
  按码点查（精确、无需索引、不会读到旧索引）。换成本入口反而会引入「用户层索引滞后一拍」的漏判。

## 7. 验收

- 在五笔里给系统词库没有的码加一个单字 → 悬停该字显示新编码；辅助码引用五笔时能用新编码筛到它。
- 在拼音里造词，五笔的用户层**不**重建（分方案写代次）；在五笔里加词，下一次查询起能查到。
- 主码表、联想方案、辅助码引用方案三者不同时，反查索引三份都保留，来回使用不触发重建。
- 用户层未就绪时，编码显示与辅助码只用系统层，不阻塞按键线程。
- 词语联想、加词去重行为不变（第一期不迁，回归测试兜底）。
